🎙️ 60-Second Interview Pitch (Say This to the Interviewer)

Problem: “Students frequently lose ID cards, calculators, keys, and bags on campus, while found-item notices are scattered across social media or WhatsApp groups.”

Solution: “I built a centralized web application that allows students to report lost belongings or register found items, and automatically pairs them using an explainable smart matching engine.”

Smart Matching: “Instead of using complex or unpredictable AI, I engineered a transparent 100-point weighted similarity algorithm that scores Category (30pts), Item Name (25pts), Location (20pts), Date Proximity (15pts), and Description keywords (10pts).”

Tech Stack: “I used pure HTML, CSS, and Vanilla JavaScript for the frontend, Python FastAPI with Pydantic for validation on the backend, and SQLite for lightweight relational storage.”

Key Takeaway: “I gained end-to-end understanding of client-server communication, RESTful status codes, relational database normalization, deterministic scoring algorithms, and full-stack state management.”

🗄️ Relational Database Design (SQLite)

The system models three core entities in Third Normal Form (3NF) to eliminate redundancy:

1. `users` Table

  • id INTEGER PRIMARY KEY AUTOINCREMENT
  • name TEXT (Full name of student/staff)
  • email TEXT UNIQUE (Campus email identity)
  • password TEXT (Salted SHA-256 hash)
  • phone TEXT (Optional contact phone)
  • created_at TIMESTAMP

2. `items` Table

  • id INTEGER PRIMARY KEY AUTOINCREMENT
  • user_id INTEGER (Foreign Key → users.id)
  • item_type TEXT ('lost' or 'found')
  • category TEXT (ID Card, Keys, Books, etc.)
  • item_name TEXT (Descriptive item title)
  • description TEXT (Details, color, contents)
  • location TEXT (Campus building / area)
  • date TEXT (YYYY-MM-DD)
  • status TEXT (Lost, Found, Possible Match, etc.)

3. `matches` Table

  • id INTEGER PRIMARY KEY AUTOINCREMENT
  • lost_item_id INTEGER (Foreign Key → items.id)
  • found_item_id INTEGER (Foreign Key → items.id)
  • match_score INTEGER (0 to 100 percentage)
  • score_breakdown TEXT (JSON breakdown)
  • status TEXT ('Suggested', 'Confirmed', 'Rejected')
  • created_at TIMESTAMP

        💬 Technical Interview Q&A Cheatsheet
      


      

        

          

            Q1: Why did you choose SQLite over MongoDB or PostgreSQL?
          

          

            “For a single-campus system, SQLite is zero-configuration, serverless, and stores everything in a self-contained disk file (lost_found.db). It supports standard ACID transactions and relational SQL foreign keys without the operational overhead, connection pooling, or memory footprint of external database servers.”
          

        


        

          

            Q2: Why use a weighted heuristic algorithm instead of an AI embedding model?
          

          

            “Explainability and determinism. When a student asks why their lost ID card was matched with a found report, we can show the exact breakdown: 30 points for category match, 25 points for item name similarity, 20 points for location proximity. It requires zero cloud API latency, zero cost, and eliminates hallucinated false matches.”
          

        


        

          

            Q3: How does your system prevent duplicate matches?
          

          

            “Whenever a new item is submitted, the matching engine runs an existence check on the matches table using composite keys (lost_item_id, found_item_id). Furthermore, resolved or closed reports are excluded from the candidate pool.”
          

        


        

          

            Q4: How do you handle security and sensitive student information?
          

          

            “Passwords are never stored in plain text; we use salted SHA-256 hashes. In addition, detailed contact information is shielded until a match is officially confirmed between the two parties, preventing unsolicited contact.”
